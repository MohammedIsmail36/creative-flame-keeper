# خطة الانفصال الكامل عن Lovable

> تاريخ الإنشاء: 2026-09-06  
> الحالة: حصر وخطة فقط؛ لم يبدأ التنظيف ولم تتغير أي بيئة  
> نقطة الأساس: الفرع `main` عند الالتزام `3f63708`

## الهدف

إزالة الاعتماد التشغيلي والبنائي على Lovable، ثم إنشاء مستودع GitHub جديد بتاريخ نظيف، من دون تغيير مصدر نشر الإنتاج الحالي أو قواعد بيانات Farida وAlibea قبل نجاح دورة Staging كاملة واعتماد المستخدم.

المقصود بالانفصال هو ألا يحتاج التثبيت أو البناء أو المصادقة أو الترحيلات أو النشر إلى نطاق أو خدمة أو حساب تابع لـLovable. لا تُحذف الإشارات التاريخية التي تلزم لفهم أصل البيانات أو قرارات الترحيل قبل نقل نسخة مختصرة ومدققة منها إلى سجل أرشيفي مناسب.

## نتيجة الحصر الأولي

| المجال | الموجود حالياً | الأثر | القرار المبدئي |
|---|---|---|---|
| تثبيت الحزم | `package-lock.json` يحتوي 111 رابط `resolved` إلى مخزن Lovable | قد يفشل `npm ci` خارج بيئة Lovable؛ npm 12 رفضها فعلاً بـ`EALLOWREMOTE` | استبدال المصدر بـnpm الرسمي مع تثبيت الإصدارات و`integrity` ثم اختبار نظيف |
| مصادقة الواجهة | `src/integrations/supabase/client.ts` يستورد `previewAuthStorage.ts` الذي يتواصل مع نطاقات محرر Lovable | لا يعمل المسار الخاص على نطاقاتنا، لكنه كود تابع للمنصة داخل حزمة التطبيق | استبداله بتخزين مصادقة محلي مستقل واختبار الدخول/التحديث/الخروج وتعدد التبويبات |
| إعداد Drizzle | `drizzle.config.ts` يقرأ `LOVABLE_DB_MIGRATION_URL` | اسم متغير مرتبط بالمنصة وقد يربك التشغيل المستقل | الانتقال إلى `DATABASE_URL` مع فحص السكربتات والوثائق وعدم تضمين أسرار |

| Migration قديم | تعليق في migration بتاريخ 2026-04-19 يذكر Lovable Cloud | تاريخي فقط ولا يغير التنفيذ | عدم تعديل migration مطبق؛ توضيح سياقه في سجل الترحيل إن لزم |
| ملفات الإرشاد | إشارات في `LOCAL_SETUP_GUIDE.md` و`ROADMAP.md` و`PRODUCTION_READINESS_AUDIT.md` وخطط التتبع | بعضها تعليمات قديمة وبعضها سجل تدقيق | تحديث التعليمات الحية، وحفظ الوقائع التاريخية بوضوح دون تقديمها كاعتماد حالي |
| Git | `origin` الحالي هو `creative-flame-keeper.git` والفرع `main` نظيف | تغييره على checkout الإنتاج قد يؤثر في `git pull` داخل سكربتات التحديث | إبقاؤه ثابتاً حتى اكتمال المستودع الجديد وStaging؛ لا force-push ولا استبدال مبكر |
| ملفات المنصة | `.gitignore` يستبعد `.lovable/`، ولا يوجد مجلد `.lovable` متعقب حالياً | لا أثر تشغيلي حالي | إزالة قاعدة التجاهل عند إنهاء التنظيف بعد التأكد من غياب الملفات |

## مستوى التعقيد والخطر

- التعقيد: متوسط؛ أغلب العمل في lockfile والمصادقة والتوثيق، بينما انتقال جدول تتبع الترحيلات يحتاج عناية أعلى.
- خطر التنظيف داخل مساحة مستقلة: منخفض جداً، لأنه لا يغير الملفات التي تخدم النطاقات ولا قواعد البيانات.
- خطر إنشاء مستودع جديد: منخفض، ما دام `origin` الحالي وسكربتات الإنتاج لم تتغير.
- خطر نشر الواجهة المنظفة: منخفض إلى متوسط ويعالج بنشر Staging أولاً ونسخة رجوع وحواجز API.
- خطر تغيير جدول تتبع الترحيلات: متوسط إلى مرتفع إن نُفذ مباشرة؛ لذلك هو دفعة قاعدة بيانات مستقلة بعد نسخة احتياطية وdry-run والتحقق على Staging.

## ضوابط غير قابلة للتجاوز

1. لا يُنفذ التنظيف داخل checkout الإنتاج `/opt/accounting-app` قبل نجاحه في مساحة مستقلة.
2. لا تتغير قواعد Farida أو Alibea خلال تنظيف الملفات أو إنشاء GitHub الجديد.
3. لا تُحذف migration مطبقة ولا يُعاد ترتيب تاريخ migrations.
4. لا يُعاد إنشاء lockfile عشوائياً؛ تثبت الإصدارات الحالية ثم تُغير المصادر فقط، وبعدها تطبق ترقية Vite المحددة كتغيير مستقل قابل للمراجعة.
5. لا تُنسخ ملفات `.env` أو مفاتيح أو نسخ قواعد أو `node_modules` أو `dist` أو مجلدات النسخ الاحتياطية إلى المستودع الجديد.
6. لا يُغير `origin` في checkout الإنتاج قبل اعتماد Staging ووجود نسخة رجوع واختبار أمر التحديث الجديد دون تنفيذ نشر.
7. لا يُستخدم `npm audit fix --force`.
8. كل دفعة لها فرق ملفات محدود، فحوص مستقلة، توثيق، والتزام Git منفصل.

## مراحل التنفيذ

### L0 — تثبيت خط الأساس ومساحة التنظيف

- إنشاء مساحة دائمة مستقلة خارج `/opt/accounting-app` وبلا `.git` من المستودع القديم.
- تسجيل بصمات `package.json` وlockfile والإعدادات وبصمات أصول Staging وFarida وAlibea.
- إعداد قائمة سماح للملفات المنقولة وقائمة منع للأسرار والمخرجات والنسخ الاحتياطية.
- لا نشر ولا تغيير remote في هذه المرحلة.

بوابة القبول: checkout الإنتاج نظيف، البيئات الثلاث HTTP 200، والخدمات والبصمات الحالية لم تتغير.

### L1 — فصل سجل الحزم

- تحويل كل `resolved` تابع لمخزن Lovable إلى `https://registry.npmjs.org/` مع إبقاء الاسم والإصدار و`integrity`.
- تشغيل `npm ci` نظيف عبر npm حديث، ثم فحص عدم بقاء أي نطاق Lovable في lockfile أو npm config المشروع.
- تشغيل التدقيق الكامل والإنتاجي ومقارنة شجرة الحزم قبل/بعد لمنع تحديثات عرضية.

بوابة القبول: صفر روابط Lovable، تثبيت نظيف، ولا اختلاف إصدارات غير مصرح به.

### L2 — فصل مصادقة المعاينة

- إزالة `previewAuthStorage.ts` وربطه من عميل Supabase، أو استبداله بوحدة محايدة إذا كانت هناك حاجة سلوكية مثبتة.
- الحفاظ على إعدادات Supabase الحالية لكل بيئة من متغيراتها الصريحة.
- اختبار تسجيل الدخول، استمرار الجلسة بعد refresh، تسجيل الخروج، انتهاء الجلسة، تعدد التبويبات، ودوري المدير والبائع على Staging.

بوابة القبول: لا نطاقات أو رسائل `postMessage` تابعة لـLovable داخل الحزمة، وكل اختبارات المصادقة ناجحة.

### L3 — تحييد أدوات قاعدة البيانات

- استبدال `LOVABLE_DB_MIGRATION_URL` باسم محايد مثل `DATABASE_URL` في الإعدادات والتعليمات، دون تسجيل قيمة سرية.
- تصميم migration مستقل ينشئ جدول تتبع محايداً وينسخ سجلات الجدول القديم دون فقد أو تكرار.
- تجربة migration وdry-run على Staging أولاً، والتحقق من أن جميع migrations تعتبر مطبقة ولا يعاد أي منها.
- يبقى الجدول القديم دون حذف حتى اعتماد الشركتين ومرور فترة رجوع متفق عليها.

بوابة القبول: تطابق سجل الترحيلات القديم والجديد، وdry-run بلا migrations قديمة معلقة، وعدم تغير بيانات الأعمال.

### L4 — تنظيف السكربتات والوثائق والهوية

- تحديث سكربتات النشر والترحيل لاستخدام الأسماء المحايدة بعد نجاح L3.
- إزالة تعليمات الربط بـLovable من دليل الإعداد وتحديث خريطة المشروع.
- إبقاء الوقائع التاريخية الضرورية في سجل واضح، مع حذف التعليمات المنتهية أو الملفات الترويجية/المولدة إن وجدت.
- فحص نصي شامل، مع تصنيف أي ذكر متبقٍ هل هو تاريخ مطلوب أم اعتماد يجب إزالته.

بوابة القبول: صفر اعتماد تشغيلي أو بنائي على Lovable، وأي ذكر متبقٍ تاريخي ومبرر صراحة.

### L5 — بوابات الجودة والأمن

- TypeScript.
- 48 ملف اختبار و563 اختباراً على الأقل.
- بناء production ومعاينة محلية وdev smoke test.
- `npm audit` كامل وإنتاجي، وفحص أسرار وتوكنات وعناوين قواعد الإنتاج داخل الملفات المتعقبة والبناء.
- بناء Staging بمتغيراته فقط والتحقق من غياب عناوين Farida وAlibea وأي عنوان Lovable.
- اختبار وظيفي يدوي للمصادقة والصلاحيات والمبيعات والمشتريات والمصروفات والتقارير والتصدير.

بوابة القبول: كل الفحوص ناجحة أو أن أي دين قديم موثق ومثبت أنه مطابق لخط الأساس وليس تراجعاً.

### L6 — مستودع GitHub الجديد

- إنشاء مستودع خاص جديد وفارغ باسم يحدده المستخدم.
- إنشاء تاريخ Git جديد من قائمة الملفات المنظفة، بدلاً من دفع تاريخ المستودع القديم بما قد يحويه من آثار أو أسرار قديمة.
- تنفيذ فحص أسرار أخير قبل الالتزام الأول، ثم دفع الفرع `main` وحمايته.
- إبقاء المستودع القديم أرشيفاً خاصاً وعدم حذفه أثناء الانتقال.

بوابة القبول: clone جديد ثم `npm ci` والفحوص والبناء ينجحون دون وصول إلى Lovable أو ملفات خارج المستودع.

### L7 — Staging ثم الإنتاج والرجوع

- ربط Staging أولاً بالمستودع الجديد أو نشر بنائه يدوياً، مع نسخة رجوع وبصمات وحواجز API.
- بعد اعتماد المستخدم، تغيير مصدر checkout الإنتاج في نافذة مستقلة مع اختبار fetch/dry-run قبل pull أو build.
- نشر Farida ثم اختبارها، وبعد الاعتماد نشر Alibea؛ لا نشر متزامن للشركتين.
- عدم تعديل قواعد البيانات ضمن دفعة الواجهة؛ ترحيل جدول التتبع له نافذة منفصلة.

بوابة القبول: النطاقات الثلاثة سليمة، البصمات موثقة، Nginx وDocker وقواعد البيانات مستقرة، وخطة الرجوع مجربة.

## خطة الرجوع

- يظل `/opt/accounting-app` وremote الحالي بلا تغيير حتى L7.
- تحفظ نسخة نشر لكل نطاق قبل استبدال الملفات.
- عند فشل الواجهة: استعادة مجلد النشر السابق وإعادة تحميل Nginx بعد `nginx -t`.
- عند فشل ترحيل تتبع migrations: إيقاف الدفعة وعدم حذف الجدول القديم؛ استخدامه كمصدر الحقيقة حتى تحليل السبب.
- لا rollback لبيانات أعمال عبر Git، ولا حذف لمستودع أو قاعدة أو جدول ضمن خطة الرجوع الآلية.

## الحالة الحالية والخطوة التالية

- مكتمل: الحصر الأولي، تقييم الخطر، ووضع الخطة.
- لم يبدأ: أي تنظيف أو نقل ملفات أو تغيير Git أو قاعدة بيانات أو نشر.
- الخطوة التالية بعد الموافقة: تنفيذ L0 فقط بإنشاء مساحة تنظيف دائمة مستقلة وتسجيل بصمات خط الأساس، مع إبقاء الإنتاج وremote الحاليين دون تغيير.
