# سجل تطوير تقرير المبيعات

> آخر تحديث: 2026-09-02
> الصفحة: `/reports/sales`  
> الحالة العامة: المراحل 1–5 و6A–6D ودفعات الاستقرار حتى S2-11 مكتملة ومعتمدة ومنشورة على الشركتين. لم تُعتمد 6E-1 وأُعيدت واجهتها إلى آخر نسخة معتمدة؛ الدفعة S2-12 مكتملة برمجياً وجاهزة للنشر على Farida.

## الغرض من الوثيقة

هذه الوثيقة هي سجل العمل الدائم لتحسين تقرير المبيعات. تحتوي القرارات المحاسبية، المراحل المكتملة، الاختبارات، الحوادث التشغيلية، المهام المتبقية، وخطوات النشر. يجب تحديثها بعد كل مرحلة وقبل الانتقال إلى المرحلة التالية.

السياسة المحاسبية التفصيلية موجودة في [`SALES_REPORT_ACCOUNTING_POLICY.md`](./SALES_REPORT_ACCOUNTING_POLICY.md).

## بنية النظام والشركات

الكود واحد، لكن كل شركة لها قاعدة بيانات وواجهة منشورة مستقلتان:

| الشركة | الواجهة | API الصحيح | مجلد النشر |
|---|---|---|---|
| Farida | `https://farida.alibea2020.com` | `https://farida.alibea2020.com/api` | `/var/www/farida` |
| Alibea | `https://alibea.alibea2020.com` | `https://alibea.alibea2020.com/api` | `/var/www/alibea` |

### قاعدة نشر إلزامية

- يجب بناء الواجهة مرة مستقلة لكل شركة باستخدام `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` الخاصين بها.
- يُمنع نسخ ناتج `npm run build` العام إلى أي موقع إنتاج؛ ملف `.env` العام يشير إلى مشروع Supabase قديم ولا يمثل أياً من بيئتي الإنتاج الذاتيتين.
- قبل النسخ يجب فحص أن ملف JavaScript الرئيسي يحتوي عنوان API المطلوب ولا يحتوي عنوان المشروع القديم.
- بعد النسخ يجب مطابقة بصمة `assets/index-*.js` بين `dist/index.html`، مجلد الموقع، والاستجابة الفعلية للنطاق.
- نشر Farida لا يعني نشر Alibea، والعكس صحيح.

## القرارات المحاسبية المعتمدة

- المؤشرات المالية تعتمد المستندات بحالة `posted` فقط.
- الضريبة لا تدخل في إيراد المبيعات أو الربح.
- الخصومات وخصم الولاء مضمنة بالفعل في إجمالي المستند ولا تُطرح مرة ثانية.
- المرتجع مستند مستقل تماماً، ويُحتسب حسب `return_date` من دون اشتراط ارتباطه بفاتورة أصلية.
- تكلفة البضاعة الصافية = تكلفة حركات `sale` ناقص تكلفة حركات `sale_return`.
- إجمالي الربح = صافي المبيعات قبل الضريبة ناقص تكلفة البضاعة الصافية.
- هامش الربح لا يُعرض إذا كان صافي المبيعات صفراً أو سالباً.
- ربح الفاتورة المفردة سيُسمى «ربح الفاتورة قبل المرتجعات المستقلة».
- التقريب المالي المعروض إلى منزلتين عشريتين.

## الأعمال المكتملة

### المرحلة 1 — القواعد المحاسبية

- إضافة مصدر حساب موحد في `src/features/sales-report/domain/metrics.ts`.
- إضافة اختبارات للضريبة، الحالات غير المرحلة، المرتجع المستقل، انعكاس تكلفة المرتجع، التقريب، والقيم الصفرية الصحيحة.
- اعتماد `net_total ?? total` بدلاً من `net_total || total` حتى لا تضيع القيمة الصفرية الصحيحة.
- توثيق السياسة في `docs/SALES_REPORT_ACCOUNTING_POLICY.md`.

### المرحلة 2 — تجاوز حد 1000 سجل

- تحويل مصادر التقرير الخمسة إلى تحميل مجزأ بدفعات قدرها 500 سجل.
- الحد الآمن الحالي لتقرير المبيعات هو 250,000 سجل لكل مصدر.
- إضافة ترتيب ثابت بالتاريخ ثم `id` لمنع التكرار أو الفقد بين الصفحات.
- توحيد حالة التحميل لجميع المصادر: الفواتير، المرتجعات، حركات المخزون، وفترة المقارنة.
- منع عرض نتائج جزئية إذا فشل مصدر واحد، وإظهار زر «إعادة المحاولة».
- تعديل أداة التحميل كي تفشل بوضوح عند تجاوز الحد الآمن بدلاً من إرجاع تقرير ناقص بصمت.
- إضافة اختبار فعلي لجلب 1,205 سجلات على ثلاث دفعات.

### المرحلة 3 — مؤشرات الأداء المالية

- ربط بطاقات التقرير بدالة الحساب المحاسبية المختبرة.
- حساب المبيعات والمرتجعات وصافي المبيعات قبل الضريبة.
- عكس تكلفة المرتجعات عند حساب صافي تكلفة البضاعة والربح.
- عرض هامش الربح من المصدر الموحد.
- جعل المؤشرات المالية ثابتة على المستندات المرحلة، مع توضيح أن فلتر الحالة يخص تفاصيل الجدول.
- تحديث ملخص التصدير ليذكر «قبل الضريبة» ويحتوي صافي التكلفة وإجمالي الربح.

## حادثة اتصال Farida بقاعدة خاطئة

### العرض

ظهر تقرير أغسطس بعدد 54 فاتورة وإجمالي 97,575 بدلاً من 58 فاتورة وإجمالي 105,250، واختفت ظاهرياً فواتير العمل حتى يوم 31.

### السبب الجذري

تم إنشاء بناء عام عبر `npm run build` ثم نسخه إلى `/var/www/farida`. أخذ البناء عنوان مشروع Supabase القديم من `.env` بدلاً من API الخاص بـFarida، فأصبحت واجهة Farida تقرأ قاعدة قديمة تحتوي 54 فاتورة.

### أثر الحادثة

- لم تُفقد البيانات.
- الفواتير الأربع كانت موجودة في قاعدة Farida الصحيحة.
- الفرق كان 7,675 في المبيعات و5,595 في التكلفة و2,080 في الربح.

### الإصلاح والتحقق

- أُعيد بناء الواجهة باستخدام API الخاص بـFarida.
- نُشر البناء المصحح على `/var/www/farida`.
- طابقت بصمة الملف المنشور الملف الذي يقدمه النطاق.
- تم التأكد أن البناء لا يحتوي عنوان مشروع Supabase القديم.
- تم التأكد أن واجهة Alibea ما زالت تحتوي API الخاص بـAlibea.

## تحصين النشر — مكتمل

تم تحصين `scripts/deploy-all.sh` قبل بدء المرحلة الرابعة:

- يتوقف السكربت فعلياً عند فشل بناء أو نسخ أو تحقق، ولا يحول الفشل إلى نجاح.
- يتحقق من API المضمّن داخل ملف JavaScript قبل لمس ملفات الموقع.
- يستخدم `rsync --delete --delay-updates` لتقليل فترة الملفات المختلطة وحذف الحزم القديمة بأمان.
- يتحقق بعد النسخ من تطابق `index.html` ووجود الحزمة واحتوائها API الصحيح.
- يطلب الصفحة من النطاق بعد النشر ويطابق بصمة الحزمة التي يقدمها الخادم.
- يرفض اسم شركة غير `farida` أو `alibea`.
- يعتمد `npm ci` فقط، ويتحقق صراحة من تثبيت `vite` حتى إذا أعاد npm رمز نجاح خاطئاً.
- أضيف وضع `--dry-run` الذي يعطل السحب والـmigrations والدوال والنشر، ثم يبني ويفحص API فقط.
- اجتاز السكربت فحص Bash واختبارات الخيارات و`dry-run` كاملاً على Farida.

### أوامر الواجهة الموصى بها

فحص Farida من دون تغيير الإنتاج:

```bash
./scripts/deploy-all.sh --dry-run --only farida
```

نشر واجهة Farida فقط من الكود المحلي، من دون سحب Git أو تغيير قاعدة البيانات أو الدوال:

```bash
./scripts/deploy-all.sh --no-pull --skip-db --skip-functions --only farida
```

استبدل `farida` بـ`alibea` لنشر الشركة الثانية. لا تستخدم ناتج بناء شركة لنشر الشركة الأخرى.

### ملاحظات بنية تحتية متبقية

- الخادم يعمل حالياً على Node.js 18، بينما عدة حزم مثبتة تعلن أن الحد الأدنى المطلوب Node.js 22. البناء ينجح حالياً، لكن يجب جدولة ترقية Node إلى إصدار 22 LTS واختبار المشروع بعدها.
- أظهر `npm audit` وجود 14 تنبيهاً (10 متوسطة و4 عالية). تحتاج مراجعة مستقلة، ولا يُستخدم `npm audit fix --force` على الإنتاج دون اختبار لأنه قد يجري تغييرات كاسرة.

## المرحلة 4 — مكتملة ومنشورة ومقبولة

الهدف: ألا تختفي المرتجعات المستقلة من تفاصيل التقرير عندما لا توجد مبيعات مقابلة لها في الفترة نفسها.

### الأعمال المنفذة

- بُني التجميع من اتحاد المفاتيح الموجودة في المبيعات والمرتجعات بدلاً من بدء التجميع من المبيعات فقط.
- طُبق الاتحاد على العملاء والمنتجات والتصنيفات والفترات الزمنية.
- أضيفت شارة «مرتجع فقط» للصفوف ذات المبيعات الصفرية والمرتجعات الموجبة.
- سُمي ربح الفاتورة المفردة «الربح قبل المرتجعات المستقلة».
- أضيف تبويب مستقل لمستندات المرتجعات مع رابط المستند وتاريخه وعميله وبنوده وقيمته قبل الضريبة.
- حُدث التصدير ليشمل تبويب المرتجعات والصفوف الجديدة وقيم المبيعات والمرتجعات المنفصلة.
- أصبحت خريطة المنتج إلى التصنيف مبنية من بنود المبيعات والمرتجعات معاً.
- استُخدمت `net_total` الصحيحة للبنود، مع الحفاظ على الصفر الحقيقي.
- أضيفت اختبارات لاتحاد المفاتيح ولتجميع أكثر من مرتجع مستقل تحت المفتاح نفسه.
- تمت مطابقة حالة Farida الحقيقية: المنتج «هوت شورت 3 قطع» بقيمة مرتجع 250 وكمية 1 يجب أن يظهر كـ«مرتجع فقط» رغم عدم بيعه في أغسطس.

### شروط قبول المرحلة 4

- يظهر المنتج المرتجع حتى إذا لم يُبع خلال الفترة.
- يظهر العميل صاحب المرتجع حتى إذا لم توجد له فاتورة مبيعات خلال الفترة.
- يظهر التصنيف المرتجع فقط بقيم سالبة/مرتجعات صحيحة.
- مجموع صافي الإيراد في كل تجميع يساوي بطاقة صافي المبيعات لنفس النطاق.
- لا يتغير تعريف المرتجع كمستند مستقل.
- فحص TypeScript ناجح، و461 اختباراً من 461 ناجحة، وبناء الإنتاج ناجح.
- تُحفظ المرحلة في commit مستقل، ثم تُرفع وتُنشر على Farida وتُختبر قبل المرحلة 5.

## المرحلة 5 — مكتملة برمجياً وبانتظار اختبار الإنتاج

### القرار المحاسبي

- لا يُستخدم `sales_invoices.paid_amount` كمبلغ تحصيل نقدي؛ فهو يساوي تخصيصات الدفعات مضافاً إليها تسويات أرصدة المرتجعات.
- التحصيل النقدي/البنكي يؤخذ من `customer_payment_allocations` المرتبطة بسندات قبض مُرحّلة.
- تسوية المرتجع تؤخذ مستقلة من `sales_invoice_return_settlements` بشرط أن تكون الفاتورة والمرتجع مُرحّلين.
- نطاق المؤشرين هو الفواتير المُرحّلة التي يقع `invoice_date` الخاص بها داخل فترة التقرير، بصرف النظر عن تاريخ إنشاء التخصيص أو التسوية؛ أي أنهما يقيسان **تغطية فواتير الفترة** وليس حركة الخزينة خلال الفترة.
- مقام النسبة هو إجمالي الفواتير المختارة **شامل الضريبة**، لأنه نفس رصيد الذمم الذي تسويه الدفعات وأرصدة المرتجعات.
- لا تُقص النسبة عند 100% حتى يظهر أي تخصيص زائد ويُمكن مراجعته.

### الأعمال المنفذة

- إضافة مصدر حساب مختبر يفصل التحصيل النقدي، تسويات المرتجعات، إجمالي التغطية والمتبقي لكل فاتورة وللفترة.
