# سجل تطوير تقرير المبيعات

> آخر تحديث: 2026-09-05
> الصفحة: `/reports/sales`  
> الحالة العامة: المراحل 1–5 و6A–6D و7 و8 ودفعات الاستقرار حتى S2-26/9D-2A مكتملة ومعتمدة ومنشورة على الشركتين. نُفذت 9D-2B واختبارات تعديل الفاتورة وحفظ المسودة الذري في Git، لكن نشرها على الإنتاج متوقف عمداً إلى أن تنجح دورة الاختبار على مشروع Staging الجديد. قاعدة Staging أصبحت مهيأة بجميع المايجريشن وبمستخدم مدير؛ المتبقي هو بيانات الاختبار وواجهة منفصلة يمكن فتحها من المتصفح. لم تُعتمد 6E-1 وأُعيدت واجهتها إلى آخر نسخة معتمدة.

## الغرض من الوثيقة

هذه الوثيقة هي سجل العمل الدائم لتحسين تقرير المبيعات. تحتوي القرارات المحاسبية، المراحل المكتملة، الاختبارات، الحوادث التشغيلية، المهام المتبقية، وخطوات النشر. يجب تحديثها بعد كل مرحلة وقبل الانتقال إلى المرحلة التالية.

السياسة المحاسبية التفصيلية موجودة في [`SALES_REPORT_ACCOUNTING_POLICY.md`](./SALES_REPORT_ACCOUNTING_POLICY.md).

## بنية النظام والشركات

الكود واحد، لكن كل شركة لها قاعدة بيانات وواجهة منشورة مستقلتان:

| الشركة | الواجهة | API الصحيح | مجلد النشر |
|---|---|---|---|
| Farida | `https://farida.alibea2020.com` | `https://farida.alibea2020.com/api` | `/var/www/farida` |
| Alibea | `https://alibea.alibea2020.com` | `https://alibea.alibea2020.com/api` | `/var/www/alibea` |

### قاعدة نشر إلزامية

- يجب بناء الواجهة مرة مستقلة لكل شركة باستخدام `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` الخاصين بها.
- يُمنع نسخ ناتج `npm run build` العام إلى أي موقع إنتاج؛ ملف `.env` العام يشير إلى مشروع Supabase قديم ولا يمثل أياً من بيئتي الإنتاج الذاتيتين.
- قبل النسخ يجب فحص أن ملف JavaScript الرئيسي يحتوي عنوان API المطلوب ولا يحتوي عنوان المشروع القديم.
- بعد النسخ يجب مطابقة بصمة `assets/index-*.js` بين `dist/index.html`، مجلد الموقع، والاستجابة الفعلية للنطاق.
- نشر Farida لا يعني نشر Alibea، والعكس صحيح.

## القرارات المحاسبية المعتمدة

- المؤشرات المالية تعتمد المستندات بحالة `posted` فقط.
- الضريبة لا تدخل في إيراد المبيعات أو الربح.
- الخصومات وخصم الولاء مضمنة بالفعل في إجمالي المستند ولا تُطرح مرة ثانية.
- المرتجع مستند مستقل تماماً، ويُحتسب حسب `return_date` من دون اشتراط ارتباطه بفاتورة أصلية.
- تكلفة البضاعة الصافية = تكلفة حركات `sale` ناقص تكلفة حركات `sale_return`.
- لا تدخل حركة التسوية الجردية `adjustment` في تقرير المبيعات؛ يظهر عجزها أو فائضها منفصلاً ضمن نتيجة النشاط وقيمة المخزون.
- إجمالي الربح = صافي المبيعات قبل الضريبة ناقص تكلفة البضاعة الصافية.
- هامش الربح لا يُعرض إذا كان صافي المبيعات صفراً أو سالباً.
- ربح الفاتورة المفردة سيُسمى «ربح الفاتورة قبل المرتجعات المستقلة».
- التقريب المالي المعروض إلى منزلتين عشريتين.

## سياسة بيئة الاختبار

- قاعدة Supabase القديمة المشار إليها من ملف `.env` أنشأتها أو تديرها Lovable، وليست مشروعاً مملوكاً للمستخدم؛ وجود رابط المشروع والمفتاح العام لا يمنح صلاحيات النسخ الاحتياطي أو المهاجرات أو إعادة التهيئة.
- يُمنع ربط نطاقَي Farida أو Alibea بهذه القاعدة القديمة، كما يُمنع استخدامها لاختبارات الكتابة أو الاعتماد عليها في أي نشر.
- تُنشأ قاعدة Supabase تجريبية جديدة في حساب يملكه المستخدم، وتُطبق عليها المهاجرات من Git وتُستخدم فيها بيانات مصطنعة فقط.
- تُنشر واجهة الاختبار في مسار أو نطاق منفصل، ولا تستبدل ملفات `/var/www/farida` أو `/var/www/alibea`.
- يُختبر عليها: إنشاء المسودة وتعديلها، ترحيل الفاتورة، فك الترحيل والتعديل وإعادة الترحيل، الإلغاء، ومرتجع البيع؛ ثم تُراجع سلامة القيود والمخزون والأرقام قبل نقل التغيير إلى الإنتاج.
- لا تُطبق migration `20260904233000_atomic_sales_invoice_draft_save.sql` على أي قاعدة إنتاج قبل نجاح هذه الدورة واعتماد المستخدم.

### الحالة الفعلية لبيئة Staging — 2026-09-05

- أنشأ المستخدم مشروع Supabase مستقلاً يملكه، بعنوان API `https://dunzfxurefzlaamgghys.supabase.co`.
- تم تسجيل Supabase CLI وربط المستودع محلياً بالمرجع `dunzfxurefzlaamgghys`، وتأكد المرجع قبل أي كتابة.
- أظهر `db push --dry-run` أن المشروع جديد وأن جميع المايجريشن المحلية مطلوبة.
- توقف التشغيل الأول عند migration `20260525102718` لأنها افترضت وجود دالتين إداريتين قديمتين خارج سجل المايجريشن. أظهر الفحص أن الدالتين غير موجودتين حالياً في Farida أو Alibea أيضاً، فتم جعل سحب الصلاحية شرطياً عند وجودهما فقط؛ هذا إصلاح لإمكانية بناء قاعدة جديدة من الصفر ولا يضيف صلاحيات جديدة.
- اكتمل `db push` حتى migration `20260904233000_atomic_sales_invoice_draft_save.sql`، ثم أثبت `migration list --linked` تطابق كل قيم `Local` و`Remote`.
- أُنشئ المستخدم الوهمي المؤكد `admin.staging@example.com` وتحقق أن دوره `admin`. كلمة مروره لم تُحفظ في Git أو في هذه الوثيقة.
- لم تُنشأ بيانات تجريبية بعد، ولم تُبن أو تُنشر واجهة Staging بعد، ولم يحدث أي تعديل على قاعدتي أو واجهتي الإنتاج خلال تجهيز هذه البيئة.
- الخطوة التالية: إنشاء واجهة منفصلة مرتبطة بقاعدة Staging. الواجهة الحالية مبنية للعمل من جذر النطاق `/`؛ إذا نُشرت تحت `/staging/` من دون دعم مسار أساسي اختياري ستفشل روابط ملفات JavaScript والتنقل. لذلك يجب أولاً إضافة إعداد بناء اختياري للمسار، مع إبقاء القيمة الافتراضية `/` للإنتاج.
- أضيف إعداد `VITE_APP_BASE_PATH` إلى Vite وربط `BrowserRouter` بالقيمة الناتجة، وصُححت الوصلات المباشرة التي كانت تتجاوز React Router. القيمة الافتراضية ما زالت `/`، لذلك لا يتغير بناء Farida أو Alibea ما لم يُمرر المتغير صراحة.
- نجح فحص TypeScript، ونجح بناء تحقق معزول داخل `/tmp/accounting-staging-path-check`. أثبت `index.html` أن JavaScript وCSS يُطلبان من `/staging/assets/` وأن حزمة التطبيق تعرف المسار نفسه. استخدم البناء عنوان API وهمياً ولم يُنشر.
- الخطوة التالية: الحصول آلياً على المفتاح العام لمشروع Staging وبناء نسخة فعلية مرتبطة به؛ بعدها يُفحص الناتج قبل تجهيز مسار Nginx المنفصل.
