اعتماد الترتيب على **رقم القيد المعتمد (posted_number)** ثم **تاريخ القيد**، بدل الترتيب الحالي المعتمد على المعرّف الداخلي / وقت الإنشاء.

## الوضع الحالي (تم التحقق منه)
- دفتر الأستاذ: دالة `get_ledger_lines` ترتّب بـ `ORDER BY entry_date, created_at` — والرصيد التراكمي (running balance) يُحسب بنفس هذا الترتيب.
- قيود اليومية: صفحة `Journal.tsx` ترتّب بـ `entry_number` تنازلياً (الرقم التسلسلي الداخلي للمسودة)، وكذلك التصدير.

المشكلة: قيد اعتُمد لاحقاً (created_at / entry_number أكبر) قد يحمل رقم قيد معتمد أصغر، فيظهر في مكان خاطئ ويختل تسلسل الرصيد التراكمي.

## التغييرات

### 1. دفتر الأستاذ (migration على `get_ledger_lines`)
- تغيير كل عبارات الترتيب الثلاث (نافذة الرصيد التراكمي + ترتيب الصفحات) إلى:
  `ORDER BY entry_posted_number NULLS LAST, entry_date, created_at`
- بما أن الدالة تعرض القيود المعتمدة فقط (`status = 'posted'`)، فقيمة `posted_number` موجودة دائماً عملياً، و`NULLS LAST` + `created_at` يبقيان كضمان احتياطي.
- الرصيد التراكمي سيتبع نفس الترتيب الجديد فيصبح متسقاً مع ما يُعرض.

### 2. قيود اليومية (`src/pages/Journal.tsx`)
- ترتيب القائمة والتصدير:
  `.order("posted_number", { ascending: false, nullsFirst: true })` ثم `.order("entry_date", { ascending: false })` ثم `.order("entry_number", { ascending: false })`
- المسودات (بدون `posted_number`) تظهر في الأعلى، ثم القيود المعتمدة تنازلياً برقم القيد ثم التاريخ.

## تفاصيل تقنية
- ملف migration جديد يعيد إنشاء `get_ledger_lines` بنفس التوقيع والصلاحيات (`GRANT EXECUTE ... TO authenticated` فقط) مع تعديل الترتيب.
- تحديث نفس تعريف الدالة داخل `public/full-schema.sql` ليبقى ملف السكيما الكامل مطابقاً للسيرفر الذاتي.
- لا تغيير في الواجهة أو الأعمدة المعروضة.

## التحقق
- فتح دفتر الأستاذ لحساب به قيود مؤرخة بترتيب مخالف لترتيب الاعتماد والتأكد من تسلسل الأرقام والرصيد التراكمي.
- فتح شاشة قيود اليومية والتأكد من ترتيب الأرقام تنازلياً وظهور المسودات أولاً.
